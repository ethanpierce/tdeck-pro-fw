# T-Deck Pro bench record — 2026-10-16

Handheld OS 0.1 was built, flashed and tested on macOS with a physical
T-Deck Pro. The original starter was flashed first, then the on-device
Settings app and network-query controls were added and tested. Device-specific
identifiers, raw serial logs, camera images and factory dumps are kept locally
and are not included in this public repository.

## Hardware and recovery

- ESP32-S3 revision v0.2; Winbond JEDEC `ef:4018`; detected flash 16 MiB.
- Firmware auto-detected board v1.1; the factory screen also identified v1.1.
  The enclosure was not opened to inspect the PCB marking.
- USB VID/PID `303a:1001`, connected directly to the Mac.
- A complete **16,777,216-byte original ESP32 flash backup** was saved before
  the first upload, with a second local copy. Every saved read passed a
  device-side MD5 check; the assembled dump also matched a device-side MD5
  of the full 16 MiB. Both copies and their manifest remain outside Git.
- Large reads with newer esptool stubs stalled; JTAG reads reported CRC errors.
  Successful recovery used verified 4 KiB reads with esptool 5.3.1 and 4.5.1.
  These workarounds were needed for backup, not normal firmware uploads.

## Software and upload

Python 3.12.14; PlatformIO Core 6.1.19; Espressif32 6.10.0; Arduino ESP32
2.0.17. Libraries and board settings are pinned in `platformio.ini`.

```sh
bash tools/test.sh
pio run -e tdeck-pro
pio run -e tdeck-pro -t upload --upload-port PORT
```

- Core: 811 checks plus 12,000 malformed packet pairs passed.
- Message store: 48 checks passed.
- Cellular service: all nine simulation scenarios passed, including APN apply,
  profile reuse after reconnect, command rejection and a 90-second scan.
- Settings: APN validation, restart persistence, independent NVS namespace,
  failed-write rollback and corrupt/truncated record recovery passed.
- Python bench and packaging utilities passed syntax compilation.
- Settings firmware uploaded successfully; esptool verified all four image
  hashes (bootloader, partitions, boot metadata and application).

Final renamed build: application usage **426,089 bytes**, static RAM
**21,296 bytes**; app image 426,448 bytes. SHA-256 of
`.pio/build/tdeck-pro/firmware.bin`:

```text
82be4ef8d56ee6d567496fc8e52c74b502ad1d8033ee884d2b63cd3ba71c7092
```

All four upload hashes verified again. USB `help` identified Handheld OS 0.1;
post-upload status confirmed ready keyboard/SIM/radio, retained APN and light
choices, NVS history, and zero dropped events. BRIO confirmed the renamed
launcher header/footer and Settings screen with the retained APN/light choices.

## Network results

An explicit `AT+COPS=?` scan took about 57 seconds and returned:

```text
(1,"AT&T","AT&T","310410",7)
(3,"313 100","313 100","313100",7)
```

The first entry was listed as available and the second as forbidden. `313100`
is [AT&T FirstNet](https://imsiadmin.com/hni-codes/att-firstnet-313-100/).
No T-Mobile entry was returned by this scan at this location and time. This
result does not establish universal coverage or carrier eligibility.

- Automatic operator selection was enabled (`CNMP: 2`, `COPS: 0`).
- Packet attachment was not established (`CGATT: 0`).
- After scan: `CEREG: 2,11` (emergency-only), `CSQ: 20,99` (-73 dBm),
  `CPSI: NO SERVICE,Online`.
- After restart/settling: `CEREG: 2,3` (registration denied), operator
  `313100`, while the saved APN remained in place.
- The no-service observations do not identify a single cause. The A7682E's
  limited US band support remains relevant; see [HARDWARE.md](HARDWARE.md).

No SMS, calls or LoRa payloads were sent during this session.

## Remaining acceptance checks

Held Shift/Alt and editing keys, visual transitions through every application,
battery-only boot, charging/power measurements, carrier eligibility and reliable
registration, consented two-way SMS/calls/audio, real-message persistence, and a
matching 915 MHz LoRa peer. At the end of this baseline pass, touch, GPS, Wi-Fi, Bluetooth and sleep
were not implemented. The connectivity pass below supersedes Wi-Fi/BLE status.


## Connectivity pass — later on 2026-10-16

Added Settings C for cellular carriers, W for Wi-Fi and B for Bluetooth LE.
The final source includes a NimBLE 2.5.1 keyboard HID host and authenticated
Nordic UART phone status service. Actual keyboard and phone pairing tests were
**deferred at the user's request**; Bluetooth was turned off and remains off
across the final update. Its setup screens remain available.

- Five host binaries passed under ASan/UBSan: existing 811 core checks plus
  12,000 malformed SMS/radio pairs; 48 message-store checks; ten modem-service
  scenarios; APN/wireless persistence, old-record preservation and corrupt/write
  failure cases; carrier/Wi-Fi/BLE/HID fixtures plus 6,000 malformed HID inputs.
- Wi-Fi found 16 nearby network results. The user selected a network, entered
  the password on the device and successfully connected. An initial failed
  attempt and subsequent retry were observed. No password was printed to USB.
- After the final upload/reset, the saved Wi-Fi connection returned by about
  3.8 seconds and a DHCP address was present. APN and both light choices also
  remained intact. SSID, password and local IP are omitted from this record.
- With Wi-Fi and BLE on together before the final update, USB reported about
  195,000 bytes free heap (minimum about 188,600 bytes), with no dropped BLE or cellular
  events. A Mac BLE scan detected Handheld OS advertising the documented Nordic
  UART service. That passive observation does not prove pairing or HID input.
- After final update with Wi-Fi connected and BLE off, USB reported 245,968
  bytes free heap, 240,216 minimum, and 8,331,903 free PSRAM bytes. The minimum
  does not establish long-term or peak-load behavior.
- The Settings carrier scan ran on the modem task while Wi-Fi and UI remained
  responsive, completing in about 58 seconds. A subsequent scan took about
  32 seconds and returned AT&T and FirstNet as available; normal LTE registration
  still reported denied. No T-Mobile entry or carrier selection change.
- No SMS, voice calls or LoRa application payloads were sent.

Final build: 1,054,129 bytes app usage in a 6,291,456-byte slot; 52,624 bytes
static RAM. The app image is 1,054,496 bytes. All four upload hashes verified.
SHA-256 of the final flashed `.pio/build/tdeck-pro/firmware.bin`:

```text
9d430375a9a524564a3a2f960e36a8f0ad38e72066d28ea5a1ef4d9a122ec6dd
```

BLE keyboard/phone authentication, bonding/reconnect and simultaneous central /
peripheral use remain unverified on hardware. Wi-Fi Internet reachability,
enterprise networks, captive portals and long-term reconnect behavior were not
tested. See [CONNECTIVITY.md](CONNECTIVITY.md) for exact controls and limits.
Meshtastic capacity was assessed from the board/partition sizes and its official
v1.1 target; no Meshtastic source has been integrated or flashed.

## Integration pass — AT&T, cellular indicators and AI Chat

This later pass supersedes the earlier no-service result for the original SIM.
The image hashes and size figures above identify those earlier builds; they are
not a hash or size claim for the integrated release image.

- An activated AT&T prepaid SIM registered on **LTE Band 5** with the saved
  **`NXTGENPHONE`** APN. `CGATT: 1` confirmed packet attachment; PDP contexts 1
  and 8 reported active. These observations apply to this device, SIM and local
  coverage, and do not establish compatibility for every AT&T plan or area.
- One explicitly authorized outbound test SMS was submitted by the modem, and
  the consenting recipient confirmed receiving it. The user reported sending
  a reply, but that reply was not found in either inspected store. SM contained
  five messages in five slots, all unsupported multipart carrier welcome
  messages; ME reported zero messages in 180 slots. This does **not** establish
  a decoder failure or successful inbound delivery. No further test SMS or
  voice call was sent during this diagnostic pass.
- The explicit `modem inbox-me` diagnostic inspected ME through CPMS mem1 and
  restored SM afterward. A subsequent query showed all three CPMS stores set
  to SM. Notification setup was `CNMI: 2,1,0,0,0`; service queries returned
  `CSMS: 0,1,1,1` and `CGSMS: 3`. Reading may mark messages read; no stored
  messages were deleted. Raw PDUs and recipient identifiers remain private.
- Read-only voice readiness queries reported IMS configuration switch **on**,
  `CSDVC: 1`, `CMUT: 0` and `VMUTE: 0`. An enabled IMS configuration switch is
  **not proof of IMS registration**, carrier voice eligibility, successful
  calling or working audio. Voice calls and audio remain untested.
- The top bar now includes the cellular technology label, four signal bars and
  battery percentage. Registration transitions trigger a fresh system-mode
  query so an earlier no-service response does not leave the LTE label stale.
- The radio service now polls the SX1262 DIO1 level on the SPI-owning task,
  avoiding the GPIO ISR installation path associated with an earlier IPC/ISR
  panic. No subsequent panic was observed during approximately 12 minutes of
  bench operation. A matching LoRa peer was unavailable; this is not a
  transmission/reception or long-term stability test.
- All **six host test binaries** passed with ASan/UBSan, including **19 modem
  service simulations** and the AI protocol/settings tests. ME inspection tests
  cover supported-message import, an interleaved SIM notification, unavailable
  ME storage, failed SM restoration, timeout recovery and refusal to interrupt
  an SMS. They do not substitute for receiving a real reply on the device.
- The AI Chat app was built and flashed. Entry of a live provider API key and
  a live request/response test are still pending. No provider success is
  claimed from the host tests or the presence of its setup screen.
- Bluetooth remains off; keyboard and phone pairing tests remain deferred at
  the user's request. Meshtastic is still not integrated; the LoRa app continues
  to use the independent Handheld OS protocol.

Remaining hardware checks include a confirmed incoming SMS, voice/audio,
matching-peer LoRa messages, a live AI request, battery-only boot and sustained
operation. No IMEI, IMSI, phone number, Wi-Fi network name, password, local IP,
API key or raw message PDU is included in this public record.
